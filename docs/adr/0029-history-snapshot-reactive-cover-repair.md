# ADR-0029: 历史记录快照过期封面按需响应式自愈架构

## 状态
已采纳 (Accepted) - 2026-11-22

## 上下文与问题陈述
客户端浏览历史列表（`UserHistoryViewModel`）通过服务端接口 `api/user/read/item/get` 分页拉取用户的浏览足迹。
该接口返回的 `cover` 字段是服务端在用户写入历史那一刻所记录的快照路径：
1. **服务端路径失效 (404 风险)**：当服务端运营后台对旧条目重新落盘封面、替换图片 CDN 分发路径或升级变体规则后，历史快照中的旧路径将直接返回 HTTP 404；
2. **全量前置刷新的性能灾难 (N+1 请求风暴)**：
   若在拉取历史列表后，前置对每条记录都调用一遍条目详情接口以获取最新真实封面，则一页 50 条历史将瞬间并发发起 50 次详情 API 请求。这不仅会导致用户流量剧烈消耗、服务端限流风暴，还会引发主界面滑动卡顿；
3. **不可见与未破坏路径的无谓浪费**：绝大多数历史条目的封面路径长期有效，只有极小比例的封面存在 404 失效。

## 候选方案评估
### 方案 A: 列表拉取后前置批量查详情回填
- 优点：列表展示前数据已对齐最新状态；
- 缺点：产生严重的 N+1 请求风暴，耗电与流量急剧上升，触发服务端高频限流。

### 方案 B: 本地持久化建立历史封面全量映射表
- 优点：无需重复请求服务端详情；
- 缺点：历史记录是全局多端同步的，跨设备同步的历史无法命中本地缓存；且条目数量巨大时 DataStore 占用膨胀。

### 方案 C: 基于图片加载失败事件的按需响应式自愈 (Reactive Healing on Failure)
- 优点：
  - 零前置额外网络开销：正常显示的图片不产生任何额外请求；
  - 精确命中：仅当图片组件（`PoiAsyncImage`）实际触发 `loadFailed` 时，才发起针对该条目的详情回源查询；
  - 局部状态更新：按 `rowId` 精确就地替换列表中对应项的 `cover` 路径，页面其余条目与滚动位置不受影响。
- 缺点：图片失败时会经历一次“占位图 -> 回源成功 -> 正常渲染”的异步修复过程。

## 决策结论
采纳方案 C，在 `UserHistoryViewModel` 中建立基于加载失败回调的按需响应式封面自愈回路：
1. **懒触发自愈**：通过 `onCoverLoadFailed(rowId, detailId, category)` 暴露单条失败接缝；
2. **精准单条回源**：仅针对失败实体发起一次轻量详情查询（如手办 `getItemDetail` 或相册 `getAlbumDetail`），取得服务端当前最新 `cover`；
3. **列表行原子替换**：以历史记录唯一主键 `rowId` 命中列表项，仅替换 `cover` 字段并落入状态流；
4. **单次防御熔断**：单条记录若回源失败或新封面仍无法加载，不再重复递归请求，避免死循环。

## 影响
- 彻底根治历史列表中因服务端图片重构导致的陈旧快照 404 破损问题；
- 规避了 N+1 请求风暴，网络请求数与首屏渲染耗时保持最优；
- 代码逻辑收敛于 ViewModel 回源方法内，不侵入 UI 层展示逻辑。
